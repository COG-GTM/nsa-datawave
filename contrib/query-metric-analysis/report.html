01 / Locate the change

Volume is counted by query creation date. Timing excludes missing, unset, invalid, or ambiguous first-page measurements; hover for denominators.

02 / Identify affected query logic

Boxes show the middle 50%; whiskers show the 5th and 95th percentiles, not extrema. Outline = before; filled = after. The suspected date belongs to “after.”

03 / Check recorded failures

Nonblank error code/message or TIMEOUT/NEXTTIMEOUT lifecycle. Not a claim that every other query succeeded.

Hover shows errors / known-status queries. Unknown error status is excluded from the rate, not from query volume.

04 / Look for associations

Association is not explanation

Rank correlations use complete pairs in the current selection, split by query logic and period. Counts span the query; first-page timing spans only the first page. Missingness, query mix, and page count can confound these relationships.

Data quality and counting rules

Zero milliseconds is valid. −1 is the model’s unset timing sentinel. Other negative, noninteger, nonnumeric, or unsafe numeric values are invalid. No interpolation or replacement with lifetime.

Full-input ingestion audit (not filtered)

@@INGESTION@@

Latest snapshot per queryId, ordered by lastUpdated then numUpdates. Exact duplicates are removed; successive snapshots are not added together. Invalid identities/timestamps quarantine that query; conflicting identities or tied latest snapshots stop the pipeline. Distributed deltas must first be merged by the service.

What an engineer should investigate next

  1. Check deployments, query-logic configuration, query plans, and data/index changes around the candidate date. Compare the affected logic with the stable groups.
  2. Compare like-for-like query templates, result/page counts, date ranges, and iterator counts. Inspect scans, index selectivity, and query plans; next() and seek() counts are not records scanned.
  3. Trace first-page stalls and recorded errors through executor queues, thread pools, storage reads, and service logs. Check missing metrics and timed-out queries before drawing a latency conclusion.

Limits on the conclusion

@@LIMITATION@@

The change detector is exploratory, with one candidate step per logic and no multiple-testing correction or causal identification. A date marks a daily boundary, not an exact incident time. Filters reuse the global boundary rather than fitting tiny selections.

Failed queries may lack a returned page, so timing percentiles can understate bad experiences. No throughput, service-level objective, CPU time, or total execution-latency claim is made.

Calculated full-dataset findings and method
    @@FINDINGS@@

Detector: daily median of valid first-page durations; log(1 + milliseconds); least-squares two-level split with at least seven eligible days each side and 20 timed queries/day. Flag a candidate only at ≥50% fit improvement and ≥1.5× median increase. Choose the strongest eligible logic by fit improvement × log ratio. Percentiles use linear interpolation, matching NumPy/pandas and the browser.
